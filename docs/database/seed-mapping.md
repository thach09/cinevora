## 3. Quy Tắc Ánh Xạ ID

Khóa chính của schema mới là `BIGINT GENERATED BY DEFAULT AS IDENTITY`; khóa cũ là chuỗi
(`admin123`, `CAT01`, `M01`). Ánh xạ được chọn sao cho **máy móc, xác định, dễ kiểm tra bằng mắt**:

| Bảng | Khóa cũ | → | Khóa mới | Quy tắc |
|---|---|---|---|---|
| `categories` | `CAT01` … `CAT07` | → | `1` … `7` | `số trong mã` = `id` |
| `movies` | `M01` … `M60` | → | `1` … `60` | `số trong mã` = `id` |
| `users` | `admin123`, `thach09`, `cr7`, … | → | `1` … `11` | **thứ tự dòng** trong `users.txt` (1-based) |
| `watchlist` / `favourites` / `watch_history` / `continue_watching` | `Mxx` | → | `<số>` | dùng `id` của movie tương ứng |
| `watch_history.id` | *(không có, PK ghép)* | → | `1` … `9` | thứ tự dòng sau khi bung danh sách |

**Vì sao dùng `users` = thứ tự dòng?** CLI không có số thứ tự cho user (chỉ có username), nên
thứ tự dòng là quy tắc xác định duy nhất và ổn định. Dòng 1 luôn là `admin` → `id = 1`.

**Điểm quan trọng:** nhờ quy tắc này, id mới **giữ nguyên phần số** của mã cũ, nên đọc `M46`
trong file legacy là biết ngay `movie_id = 46`, không cần tra bảng. Toàn bộ ánh xạ cũng được
xuất ra `tools/build/seed-mapping.tsv` để đối chiếu tự động.

## 6. Quy Tắc Mật Khẩu (Bảo Mật)

| Hạng mục | Bản CLI cũ | Bản web mới |
|---|---|---|
| Nơi lưu | `users.txt` — **plaintext** | `users.password` — **BCrypt hash** |
| Giá trị | 11 mật khẩu khác nhau, **tất cả đều rất yếu** | 1 hash chung cho mọi tài khoản |
| So sánh | `String.equals()` trực tiếp | `BCryptPasswordEncoder.matches()` |
| Thuật toán | – | BCrypt, cost **10**, tiền tố `$2a$`, độ dài **60 ký tự** |

**Hash được dùng trong V2:**

```
$2a$10$RSRK4WMinzwDDi6hcY19lOHClSIggDv1DUOUB.3VEKnFQss0L4CV6
```

Hash này sinh bởi `tools/PasswordHashGenerator.java` (dùng jBCrypt 0.4 vendor trong `tools/lib`) và
được **nhúng cứng** vào `SeedSqlGenerator.java` để file V2 có thể sinh lại y hệt (deterministic).
`SeedSqlGenerator` **tự kiểm tra** `BCrypt.checkpw(DEMO_PASSWORD, DEMO_PASSWORD_HASH)` trước khi ghi
file — nếu hash sai thì dừng ngay, không sinh ra seed hỏng.

### Cơ chế phòng vệ 2 lớp chống rò rỉ plaintext

1. **`SeedSqlGenerator.assertNoPlaintext()`** — sau khi sinh SQL, quét lại file và **so chuỗi** với
   **cả 11** mật khẩu plaintext trong `users.txt`. Nếu bất kỳ giá trị nào xuất hiện → huỷ, không ghi
   file. Tool in ra `[OK] Quet bao mat: 11/11 ... KHONG xuat hien trong SQL`.
2. **Kiểm tra thủ công khi review** — xem mục 8.

## 7. Quy Tắc Sinh Thời Gian

`V2` không dùng `NOW()` — mọi mốc thời gian đều được sinh **xác định** từ một mốc gốc cố định
`2026-01-01 00:00:00+00:00`, để chạy lại generator luôn ra cùng một file:

| Bảng | Mốc | Công thức |
|---|---|---|
| `categories` | epoch **+1 ngày** | `epoch + 1 day + i × 17 phút` |
| `movies` | epoch **+2 ngày** | `epoch + 2 days + i × 17 phút` |
| `users` | epoch **+3 ngày** | `epoch + 3 days + i × 17 phút` |
| `watchlist` | epoch **+4 ngày** | `epoch + 4 days + i × 17 phút` |
| `favourites` | epoch **+5 ngày** | `epoch + 5 days + i × 17 phút` |
| `watch_history` | epoch **+6 ngày** | `epoch + 6 days + i × 17 phút` |
| `continue_watching` | epoch **+7 ngày** | `epoch + 7 days + i × 17 phút` |

* `i` = chỉ số dòng (0-based) **trong từng bảng**, nên trong mỗi bảng thứ tự tăng dần.
* `updated_at = created_at` cho mọi bảng (đơn giản, dễ kiểm tra).
* Với `watch_history`, thứ tự dòng giữ nguyên thứ tự trong `users.txt` → `watched_at` tăng dần theo
  lịch sử xem (mốc cũ nhất trước).
* Toàn bộ cột thời gian là `TIMESTAMPTZ` và ghi ở múi giờ `+00:00`.

### Kiểm tra thủ công nhanh (PowerShell — quét đủ 11 mật khẩu)

```powershell
# KHONG hard-code danh sach mat khau o day - doc truc tiep tu users.txt (cot 3).
# Neu hard-code, chi can grep vai gia tri dai dien la se bo sot phan con lai.
$legacyPasswords = (Get-Content legacy-cli\data\users.txt) |
    ForEach-Object { ($_ -split '\|')[2] } | Where-Object { $_ } | Sort-Object -Unique
if ($legacyPasswords.Count -ne 11) { throw "Chi doc duoc $($legacyPasswords.Count) mat khau, mong doi 11" }

$targets = Get-ChildItem -Recurse -File -Include *.md,*.java,*.sql,*.yml,*.yaml,*.example,*.properties,*.json,*.ps1 |
    Where-Object { $_.FullName -notmatch '\\legacy-cli\\data\\' -and $_.FullName -notmatch '\\tools\\build\\' }

$leaks = 0
foreach ($p in $legacyPasswords) {
    $hits = $targets | Select-String -SimpleMatch $p
    # KHONG in ra gia tri mat khau - chi in so dong khop
    if ($hits) { $leaks++; "LEAK: $($hits.Count) dong"; $hits | ForEach-Object { "   -> $($_.Path):$($_.LineNumber)" } }
}
if ($leaks -gt 0) { "KET QUA: FAIL ($leaks mat khau bi lo)" } else { "KET QUA: PASS (11/11 sach)" }
```

> [!CAUTION]
> Script phải kiểm tra **đủ 11** giá trị. Bản kế hoạch đầu tiên chỉ grep **3 giá trị đại diện** →
> **8 mật khẩu còn lại lọt lưới** mà vẫn tưởng repo đã sạch. Vì vậy script **không được hard-code**
> danh sách, mà đọc trực tiếp từ `legacy-cli/data/users.txt` cột 3 — nguồn chân lý duy nhất, không
> chép lại bằng trí nhớ. Ngoài ra script **không in ra giá trị mật khẩu**, chỉ in số dòng khớp, để
> log/CI không vô tình lưu lại chúng.

## 9. Ghi Chú Về Việc Xoá Dữ Liệu CLI Cũ

`legacy-cli/data/{categories,movies,users}.txt` từng chứa **11 mật khẩu plaintext**, mâu thuẫn với mục
tiêu "không còn plaintext password trong repo". Điều kiện tiên quyết để xoá là **8/8 PostgreSQL smoke test + ST9 offline PASS**
— đã thoả ngày **2026-09-15** (ST1–ST8 trên PostgreSQL 16.15 qua Docker + ST9 quét plaintext; xem
[migration-runbook.md](migration-runbook.md) §8), nên 3 file đã được xoá:

```powershell
# 1. Xác nhận có điểm khôi phục (commit cuối còn giữ ĐÚNG path legacy-cli/data/)
git log --format=%H -1 --diff-filter=AM -- legacy-cli/data/users.txt   # -> 078b5114d9b1617572b56062fc70147f4ac95bfc
# 2. Xoá khỏi working tree (vẫn phục hồi được từ git history)
git rm legacy-cli/data/users.txt legacy-cli/data/movies.txt legacy-cli/data/categories.txt
# 3. KHÔNG xoá git tag v1.0-cli-final
```

> **Đừng chạy `git checkout v1.0-cli-final -- legacy-cli/data`** (câu lệnh này từng bị ghi sai trong
